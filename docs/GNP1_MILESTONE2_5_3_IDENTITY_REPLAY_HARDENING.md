# GNP/1 M2.5.3 — Identity History & Replay Hardening

## Goal

M2.5 authenticated rename proved that a human-readable device name can change without changing Device ID, pairing trust, signing identity, or trust history. Its original `GLS1` proof authenticated the name but did not totally order old valid signed advertisements. M2.5.3 adds ordering so a captured historical signed name cannot roll a trusted peer back after a newer identity assertion has been accepted.

## GLS2 replay-protected discovery

`GLS2` is additive. Transfer protocol version remains 3 and existing `GLS1`/`GLD2` compatibility advertisements are still emitted. A GLS2 signature covers the existing signed-discovery fields plus a positive 64-bit `IdentityRevision`. The revision is therefore authenticated under the same ECDSA P-256 identity as the device name, Device ID, device kind, ports, ECDH fingerprint, signing generation, and signing public key.

The sender writes `identity-assertion-revision.json` in its local app-data directory. The value remains stable while the public signed assertion is unchanged. It advances when the public assertion changes, including device rename, device kind, signing-key generation, or signing key. The store uses bounded JSON, an atomic temporary file, and `.bak` recovery.

## Receiver acceptance rules

Trusted Identity Registry schema v4 adds `LastAcceptedIdentityRevision`. Automatic trusted-name mutation requires all existing M2.5 anchors plus a replay-protected assertion:

- Device ID is the already trusted Device ID.
- ECDH/pairing fingerprint matches the pinned pairing trust anchor.
- registry binding is `Trusted` and lifecycle is `Active`.
- identity version, signing generation, and Signing Key ID exactly match the current trusted signing identity.
- `IdentityRevision` is positive and is not lower than `LastAcceptedIdentityRevision`.
- the same already accepted revision cannot assert a different device name.

A higher accepted revision advances `LastAcceptedIdentityRevision`. A rename at that revision appends an `AuthenticatedRename` history event carrying the revision. Existing monotonic local `Sequence` remains the ordering authority for local audit events such as lifecycle transitions and key rotation.

## Downgrade/replay behavior

An M2.5.3 sender broadcasts `GLS2`, then `GLS1`, then `GLD2`. The receive loop prefers GLS2 and suppresses the immediately following compatibility GLS1 for that peer. More importantly, the trusted-device store never allows unordered GLS1 to change a saved trusted name. This closes the old-name replay path even if a historical GLS1 is later injected.

`GLS1` is retained for interoperability. A mixed-version peer can still be discovered and can still use the existing trusted transfer protocol. But a rename generated by a pre-M2.5.3 peer is not accepted as a persisted automatic rename by an M2.5.3 receiver because the old peer cannot provide an ordered GLS2 revision.

## Key rotation interaction

Identity revision does not replace M2.4.2 continuity. A packet signed by a different/new key is not allowed to rename a peer merely because its revision is larger. The new signing key must first be accepted by the existing `GLR1/GLI2` continuity process. Packets from retired signing generations fail the current trusted-signing-key check before revision ordering can authorize a rename.

## Lifecycle scope

`Active / Retired / Revoked` is still local administrative policy in this checkpoint. M2.5.3 does not propagate lifecycle commands and does not define a network administrative authority. The local identity-history `Sequence` continues to order those events on each node. Future network governance must use separately authenticated administrative authority rather than trusting a self-signed device assertion to revoke another device.

## Expected live test

1. Upgrade both trusted peers to M2.5.3 and start them.
2. Confirm a local log reports an initialized/stable identity assertion revision and discovery reports `GLS2` / that revision.
3. Confirm the peer logs `replay-protected signed discovery verified` and preserves existing Device ID, signing key, generation, trust, and transfer behavior.
4. Rename one OS/device and restart Genia Link. Its local revision must advance once.
5. The other peer must record `replay-protected authenticated rename accepted` with the higher revision, without SAS re-pair.
6. Restart both applications; the newest name and accepted revision must persist.
7. Run `scripts/SecurityCheck-Android.ps1`; self-tests inject a lower signed revision and a same-revision conflicting name and require both to fail closed.

## Security boundary

The monotonic revision provides ordering of authenticated public identity assertions; it is not a challenge/response liveness proof and does not replace the trusted transfer handshake. Loss of all local revision-store copies is treated as recovery and creates a new persisted baseline; preserving app-data and its `.bak` file is therefore part of normal identity continuity.
